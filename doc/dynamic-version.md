# A version that moves every build

A project version derived from a commit id defeats the cache: every commit is a different key, so
`native-image` runs every time even when nothing the application is built from has changed. Back to
the [README](../README.md).

Measured on two builds differing only in version, it reaches six places in the jar the native image generation is keyed on:

```
io/quarkus/runner/ApplicationImpl.class
io/quarkus/runner/recorded/ConfigGenerationBuildStep$check….class
io/quarkus/runtime/generated/BuildTimeRunTimeFixedConfigSourceBuilder.class
META-INF/MANIFEST.MF
META-INF/maven/…/pom.properties
META-INF/maven/…/pom.xml
```

Three of those are generated bytecode, which is why no amount of ignoring configuration properties helps: `quarkus.application.version` defaults to the project version and is compiled into the application.

```properties
DEVELOCITY_QUARKUS_VERSION_INDEPENDENT_BUILD=true
```

With it set, the extension builds under a `build.finalName` without the version — which otherwise names the jar and appears in `native-image.args` — and drops `META-INF/maven/**` from the jar it keys on, those files reaching nothing the native image is built from. Once the native image generation is done it links the executable back to the name it would have had, so the rest of the build finds it where it expects:

```
[INFO] [quarkus-build-caching-extension] Building as 'my-app' rather than 'my-app-1.0-abc1234', so that the version stays out of the native image cache key
[INFO] [quarkus-build-caching-extension] Linked my-app-1.0-abc1234-runner to the cached my-app-runner
```

A link rather than a move: the executable under its stable name is the declared output, and Develocity stores it once the goal is done.

**Set `quarkus.application.version` yourself** to something that does not move, or the key still changes on every commit — it defaults to the project version and is compiled in, which the extension cannot normalize away. It warns when you have not:

```
[WARNING] [quarkus-build-caching-extension] quarkus.application.version is not set, so it defaults to the project version and is compiled into the application: the native image cache key will still change on every version. Set it to a value that does not move.
```

Anything Quarkus derives from that version follows it, `quarkus.container-image.tag` in particular. Set the tag separately if it has to carry the commit id — it is regenerated by the augmentation on every build, so it does not feed the key.


## A worked recipe

[`src/it/quarkus-3.39.3-dynamic-version`](../src/it/quarkus-3.39.3-dynamic-version) is a complete project to copy from. Its version is `1.0-${sha1}`, so every build is a different version, and it runs three builds:

| | |
|---|---|
| commit `abc1234` | `native-image` runs, the entry is stored |
| commit `def5678` | **cache hit across the version change**, `native-image` does not run |
| commit `9999999`, recipe turned off | `native-image` runs again |

The [pom](../src/it/quarkus-3.39.3-dynamic-version/pom.xml) shows both properties in place, and [postbuild.groovy](../src/it/quarkus-3.39.3-dynamic-version/postbuild.groovy) the log lines to expect from each.
